# V0.3 — Governed Git Source Adapter

V0.3 upgrades WikiSkill-Evolution's `core` target from a fail-closed placeholder into a governed source-code evolution path for **pre-registered local Git repositories**.

The trust boundary is deliberately strict:

```text
trusted Source Registry + trusted Gate Registry
                    ↓
         untrusted Core proposal
                    ↓
           Git Source Adapter
                    ↓
      isolated candidate worktree
                    ↓
Static → Build → Regression → optional Performance
                    ↓
          WikiSkill held-out Gate
                    ↓
R_candidate > R_best ? accept : rollback
```

The proposal is data, not executable configuration. It cannot select a repository URL, define shell commands, alter gate profiles, widen path policy, provide credentials, or mutate binaries/model weights.

## Register a source

Source registration is an explicit operator action. V0.3 does **not** clone repositories; `repository` must already resolve to a local Git repository.

Example manifest:

```json
{
  "source_id": "wikiskill-core",
  "adapter": "git_source",
  "repository": "/absolute/path/to/WikiSkill-Evolution",
  "baseline_ref": "main",
  "baseline_sha": "7089b8b35254edc5d636461f003c6e4655535f2c",
  "write_policy": {
    "allow": ["wikiskill/**", "tests/**"],
    "deny": [".git/**", ".github/**", "workspaces/**", "models/**", "secrets/**"]
  },
  "patch_policy": {
    "max_files": 8,
    "max_total_lines": 500,
    "text_only": true
  },
  "gates": {
    "static": "registered:wikiskill-static",
    "build": "registered:wikiskill-build",
    "regression": "registered:wikiskill-regression",
    "performance": null
  }
}
```

`baseline_sha` must be the exact full commit SHA present in that local repository. The SHA above documents the V0.3 branch's original V0.2 base; use the repository's actual intended baseline when registering a real source.

Register and inspect it from a WikiSkill workspace:

```bash
wikiskill source register source.json --ws /path/to/workspace
wikiskill source list --ws /path/to/workspace
wikiskill source inspect wikiskill-core --ws /path/to/workspace
wikiskill source validate wikiskill-core --ws /path/to/workspace
```

When `--ws` is omitted, source commands use the current directory.

There is intentionally **no** `wikiskill source exec` command.

## Accepted source authority

At registration, WikiSkill creates:

```text
refs/wikiskill/<source_id>/accepted
```

This namespaced Git ref is the authoritative accepted source SHA. The workspace mirror at `sources/state/<source_id>.json` exists for audit/readability and is repaired from the Git ref if they disagree.

A later Core proposal must bind `base_sha` to the current accepted ref exactly. Acceptance advances the ref with compare-and-swap semantics; rejection leaves it unchanged.

Keeping a real Git ref also keeps an accepted candidate commit reachable after its detached worktree is removed.

## Core proposal schema

A proposer can choose only a source exposed by the trusted registry:

```json
{
  "target": "core",
  "action": "patch",
  "source_id": "wikiskill-core",
  "base_sha": "CURRENT_ACCEPTED_FULL_SHA",
  "edits": [
    {
      "file": "wikiskill/example.py",
      "op": "replace",
      "target": "exact old text",
      "content": "exact new text"
    }
  ]
}
```

Allowed edit operations are `append`, `replace`, and `insert_after`. `replace` and `insert_after` require an exact unique target. V0.3 mutates tracked UTF-8 text files only.

Before any worktree is created, the adapter rejects stale SHA bindings, path traversal, absolute paths, symlink/submodule boundaries, non-allowlisted files, denylisted files, binary/non-UTF-8 content, excessive file counts or line budgets, and proposal-supplied executable/control fields.

## Isolated candidate lifecycle

A candidate worktree is generated under:

```text
<workspace>/runs/core-worktrees/iter-<NN>-<source_id>-<short-sha>/
```

The proposal cannot choose this path. The registered source working tree is never edited directly.

The adapter preplans all text changes in memory, creates a detached worktree at the accepted SHA, writes only the planned files, and re-checks the observed Git diff against the expected file set and policy.

## Engineering Gate pipeline

The pipeline short-circuits in this order:

1. **Static Gate** — mandatory.
2. **Build Gate** — mandatory; runs only after Static passes.
3. **Regression Gate** — mandatory; runs only after Build passes.
4. **Performance Gate** — structured interface; may be `not_configured` only when the source manifest explicitly has `performance: null`.
5. **WikiSkill held-out Gate** — runs only after source engineering gates allow the candidate.

Production gate profiles are fixed trusted entries in `wikiskill/gates.py`. Profiles execute argv arrays with `shell=False`; proposals cannot add or redefine them.

The initial built-in profiles are:

- `registered:wikiskill-static`
- `registered:wikiskill-build`
- `registered:wikiskill-regression`

## Acceptance and rollback

Engineering success is necessary but not sufficient. The existing WikiSkill acceptance rule remains:

```text
R_candidate > R_best
```

If the held-out score does not strictly improve, the candidate worktree is removed and the accepted source ref remains unchanged.

On acceptance, the candidate is committed with a fixed local identity, protected by a temporary reachability ref, the worktree is removed, and the accepted namespaced ref advances by compare-and-swap. Only after source acceptance succeeds does the harness advance `R_best`.

Operational failures are recorded separately from candidate-quality rejections so the Wiki does not incorrectly learn that a patch idea was bad when infrastructure failed.

## Persistent audit

For Core candidates, Wiki/history evidence includes source ID, base/candidate/accepted SHA evidence, changed files, gate results, cleanup/finalization evidence, held-out score, final verdict, and the full proposal/diff where applicable.

Rejected and invalid experience remains persistent just like earlier WikiSkill asset candidates.

## V0.3 security boundary

V0.3 does not:

- clone/fetch a proposal-supplied repository;
- accept proposal shell commands, scripts, environment variables, credentials, or gate definitions;
- allow an agent to register a source or gate profile;
- patch binaries or model weights;
- install APKs or use ADB/Shizuku;
- perform phone thermal/power gates;
- automatically open or merge cross-repository PRs.

Those source-specific/device capabilities belong to later phases and must consume this governed adapter rather than bypass it.

## V0.4 handoff

The intended next adapters/profiles are source-specific layers on top of V0.3, such as llama.cpp C/C++/CMake validation, Android Gradle/NDK builds, inference benchmarks, APK/device acceptance, and S24/S24U TTFT/decode/memory/thermal/power gates.
