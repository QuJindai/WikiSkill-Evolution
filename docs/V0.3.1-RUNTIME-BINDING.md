# V0.3.1 Trusted Runtime Binding

V0.3.1 closes the causal gap between a governed Core source patch and the score used to accept it. A Core candidate is no longer considered capability-tested merely because its source compiles or passes regression tests: WikiSkill must prove that the exact candidate Git SHA produced the held-out task execution.

## What V0.3.1 adds

V0.3 introduced governed source mutation, isolated Git worktrees, trusted path policy, engineering Gates, and an authoritative accepted ref. V0.3.1 adds the execution layer needed to make those source changes causally testable:

```text
trusted Source Registry
        +
trusted Runtime Binding Registry
        ↓
accepted source SHA A
        ↓
detached accepted runtime at exact A
        ↓
baseline / train / non-Core held-out use A
        ↓
Core proposal + engineering Gates
        ↓
seal immutable candidate SHA B + temporary ref
        ↓
bind exact candidate worktree HEAD B
        ↓
Core held-out tasks execute B
        ↓
R_B > R_best ?
  no  → reject B, clean worktree/temp ref, keep A
  yes → close B runtime → clean candidate worktree
       → CAS accepted source A→B, keep temp ref
       → atomically persist R_best + runtime_identity(B)
       → release temp ref
        ↓
next rollout resolves accepted ref again and executes B
```

A boolean such as `candidate_runtime_bound=True` is not runtime evidence and cannot bypass this lifecycle.

## Operator workflow

Runtime registration is trusted operator state. It is separate from Core proposal JSON.

### 1. Register the governed source

```bash
wikiskill source register source.json --ws <workspace>
wikiskill source validate <source_id> --ws <workspace>
```

The source manifest fixes repository identity, accepted baseline, path policy, patch limits, and registered engineering Gate profiles.

### 2. Bind a trusted runtime profile

```bash
wikiskill runtime bind <source_id> registered:python-json-runner-v1 --ws <workspace>
wikiskill runtime inspect --ws <workspace>
```

The initial production profile is static code. Proposal data cannot register or redefine it.

### 3. Activate the inference source before scoring

```bash
wikiskill runtime activate <source_id> --ws <workspace>
```

Activation is allowed only while `state.baseline is None`. If a workspace already has a scored baseline, activation fails closed instead of silently comparing scores from different runtime epochs.

After activation, ordinary inference uses the active accepted runtime automatically:

- initial baseline → current accepted SHA;
- each iteration's train rollouts → current accepted SHA;
- Skill/Prompt/Harness held-out validation → current accepted SHA;
- CLI `run-task` → current accepted SHA;
- Maintainer and Evolution Proposer → framework/backend runner, not the governed runtime.

## Trusted runtime state

Workspace runtime state lives outside proposal data:

```text
<workspace>/runtime/
├── registrations.json
└── active.json
```

Registration stores only source/profile/role. Active state stores only the selected inference source/profile. It does not store arbitrary argv, commands, environment values, credentials, executable paths, devices, or ports.

Every accepted runtime identity is derived from trusted configuration plus the authoritative accepted ref:

```json
{
  "source_id": "demo-core",
  "binding_profile": "registered:python-json-runner-v1",
  "accepted_sha": "<exact Git SHA>",
  "fingerprint": "sha256:<canonical identity hash>"
}
```

Once a baseline exists, that identity is part of the scoring epoch. Before later scoring, WikiSkill recomputes the trusted active identity and requires an exact match. An out-of-band ref or runtime-config change stops scoring rather than silently re-baselining.

## Accepted runtime materialization

The source repository's normal working tree is never accepted-runtime authority. It may be dirty or checked out on another branch without affecting scoring.

For a rollout phase, WikiSkill creates a host-generated detached worktree under:

```text
<workspace>/runs/runtime-worktrees/
  accepted-<source>-<shortsha>-<nonce>/
```

Before execution it verifies:

- the requested source SHA resolves to a commit;
- detached worktree `HEAD` equals that exact SHA;
- the fixed entrypoint is a tracked regular file at that commit;
- the entrypoint's worktree content hashes to its Git blob SHA;
- tracked runtime files remain unchanged before each task.

The accepted runtime worktree is removed on `BoundRuntimeSession.close()`.

## Core candidate sealing and execution

After a Core candidate passes Static → Build → Regression → optional Performance, WikiSkill seals it before capability scoring:

```text
verify candidate integrity
→ stage only expected changed files
→ fixed-identity Git commit
→ create refs/wikiskill/<source_id>/candidate-<iteration>
→ record candidate SHA
```

Sealing does not move the accepted ref. The candidate worktree remains available for exact runtime binding.

For held-out validation, `bind_sha()` requires the candidate worktree to be under the workspace Core worktree root and verifies its `HEAD` equals the sealed SHA. The Core held-out Gate receives only the resulting `BoundRuntimeSession.runner` and bounded runtime evidence. There is no fallback to the accepted/default runner.

## Python JSON Runner v1

Profile:

```text
registered:python-json-runner-v1
```

Fixed contract:

- entrypoint: `wikiskill_runtime.py`;
- executable: host `sys.executable`;
- `cwd`: exact bound accepted/candidate worktree;
- `shell=False`;
- timeout: fixed by trusted profile;
- environment: minimal `PATH` + `PYTHONIOENCODING` only;
- stdin: exactly one host-built JSON request;
- stdout: exactly one JSON object with `{"status":"ok"}`.

Request shape:

```json
{
  "protocol": "wikiskill-runtime-v1",
  "prompt": "...",
  "tag": "iter-01/val/task-1",
  "workdir": "/resolved/task/sandbox",
  "max_turns": 15
}
```

The runtime writes task deliverables into the host-provided sandbox. Candidate output cannot choose trace/evidence destinations.

The profile deliberately does not forward unrelated host secrets. It is a causal execution/process boundary for trusted development sources; it is **not** a hostile-code, network, container, VM, or kernel sandbox.

## Trace evidence

Task trace metadata persists only the bounded public runtime identity:

```json
{
  "runtime": {
    "source_id": "demo-core",
    "source_sha": "<exact SHA that ran>",
    "binding_profile": "registered:python-json-runner-v1",
    "fingerprint": "sha256:..."
  }
}
```

Command lines, environment dictionaries, worktree paths, credentials, and other runtime internals are not copied into the raw task trace.

## Acceptance transaction

Strict capability semantics remain unchanged:

```text
accept only if R_candidate > R_best
```

For Core, improvement is necessary but not sufficient. Finalization is ordered:

1. candidate `BoundRuntimeSession` closes successfully;
2. candidate worktree is removed/pruned;
3. accepted source ref/state advances A→B by compare-and-swap while the candidate temp ref remains;
4. gating state atomically persists the new `R_best`, `runtime_identity(B)`, history, and next iteration;
5. candidate temp ref is released;
6. Wiki audit is committed.

If score-state persistence fails after source A→B, WikiSkill attempts a compensating source transition B→A. Successful compensation preserves the previous score/runtime epoch and records `operational_error`. If compensation fails, it records `recovery_required` when persistence is available, preserves candidate reachability, and later scoring fails closed because the authoritative accepted ref no longer matches the recorded runtime identity.

A candidate-ref deletion failure after source and score state already agree does not invent a second accepted state: the extra ref remains reachable for operator cleanup and the failure is written to the Wiki log/audit evidence.

## Failure classes

- **invalid** — malformed proposal/configuration, non-active Core source, or prohibited runtime controls;
- **rejected** — engineering Gate failure or valid candidate runtime with `R_candidate <= R_best`;
- **operational_error** — bind/process/close/worktree/CAS/state operation fails without an unresolved source/score split;
- **recovery_required** — source and score/runtime identity cannot be restored to agreement automatically.

No failure path deliberately advances `R_best` without a matching trusted runtime identity.

## Security boundary

V0.3.1 preserves these invariants:

- proposal is source-edit data, not execution configuration;
- source registration and runtime bind/activate are operator-only;
- repository identity, paths, engineering Gates, runtime profile, entrypoint, argv, environment, timeout, and executable come from trusted code/configuration;
- accepted runtime is pinned to the authoritative accepted Git SHA, never the repository checkout;
- candidate is sealed before runtime binding;
- candidate held-out cannot fall back to accepted/default execution;
- Maintainer/Proposer remain separated from the governed inference runtime;
- each scored runtime task carries the exact source SHA that ran;
- runtime/source identity mismatch fails closed;
- accepted runtime is re-resolved after Core acceptance rather than cached across later rollout phases.

## Automated causal proof

`tests/test_v031_runtime_integration.py` uses real Git repositories, real Git refs/worktrees, and a real Python subprocess protocol. It proves:

- accepted SHA A produces the baseline;
- train and non-Core held-out use A;
- a Core patch changes `wikiskill_runtime.py` and is sealed as B;
- Core held-out executes B and traces B;
- an improving B advances the accepted ref and scoring identity to B;
- a non-improving B is rejected without changing A;
- the next iteration materializes accepted B afresh;
- state-write failure compensates B→A;
- compensation failure produces a fail-closed recovery state.

Only Maintainer/Proposer behavior is stubbed in the deterministic causal fixture; source/runtime execution is real.

## Next boundary

Future profiles can reuse the same lifecycle, for example:

```text
registered:llama-cpp-cli-v1
registered:android-local-runtime-v1
```

Those profiles may add controlled build artifacts, model invocation, ADB/Shizuku routing, TTFT/decode/memory/thermal/power evidence, or credential allowlists only through separately reviewed trusted profiles. They must preserve exact source identity, sealed candidates, strict held-out improvement, transaction ordering, cleanup, audit, and fail-closed recovery.
