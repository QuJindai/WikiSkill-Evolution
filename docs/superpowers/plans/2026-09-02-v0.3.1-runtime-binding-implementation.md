# WikiSkill-Evolution V0.3.1 Trusted Runtime Binding Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Close the V0.3 causal gap by binding both accepted and candidate Core source SHAs to trusted executable runtimes, so baseline/train/held-out scores are produced by the exact source commit recorded in runtime evidence and Core acceptance can safely advance the accepted source ref.

**Architecture:** Add a static trusted runtime-binding registry plus workspace runtime registration/activation state. Split Core candidate finalization into seal → bind → held-out score → accept/reject, and route ordinary inference tasks through a detached accepted-runtime worktree resolved from the authoritative accepted ref. The first concrete profile is a fixed Python JSON protocol that never accepts proposal-supplied argv, entrypoint, timeout, environment, or credentials.

**Tech Stack:** Python 3.10+, Python stdlib only, Git CLI subprocesses, pytest, pyflakes, GitHub Actions Python 3.10/3.11/3.12 matrix.

**Spec:** `docs/superpowers/specs/2026-09-02-v0.3.1-runtime-binding-design.md`

## Global Constraints

- Base branch is `feature/v0.3-git-source-adapter@6ecea640d0d91217f4239f9f50a13030ea492cb2`; PR #3 is not modified by V0.3.1 implementation commits.
- Proposal JSON remains untrusted bounded source-edit data and MUST NOT carry runtime profile ids, argv, entrypoints, environment variables, credentials, ports, device ids, executable paths, timeouts, or runtime commands.
- Runtime binding registration and activation are explicit operator actions only.
- Only one active runtime role exists in V0.3.1: `inference`.
- Runtime activation is allowed only while `state.baseline is None`; V0.3.1 never silently re-baselines an already-scored workspace.
- Accepted runtime materialization MUST use a host-generated detached Git worktree at the authoritative accepted ref SHA; the registered repository's current checkout is never runtime authority.
- Candidate runtime binding requires a sealed immutable candidate commit and temporary reachability ref before any held-out task runs.
- A boolean flag is never sufficient binding evidence; the harness must receive a `BoundRuntimeSession` whose verified `source_sha` equals the exact accepted/candidate SHA.
- Ordinary baseline/train/val inference tasks use the active accepted runtime when configured. Maintainer and Proposer continue using the framework/backend runner.
- The active accepted runtime is re-resolved at iteration boundaries so an accepted Core commit becomes the runtime used by subsequent iterations.
- Candidate held-out tasks MUST use the candidate-bound runner, never the ordinary accepted/default runner.
- Accepted-ref advancement and score/runtime-identity advancement use a two-phase finalize sequence with compensation: source acceptance first, then state persistence; state persistence failure attempts accepted-ref rollback and leaves a recovery ref if rollback cannot be proven.
- `R_best` and `state.runtime_identity` advance only after source acceptance succeeds. Rejection or operational failure changes neither.
- Runtime proof profile passes a minimal environment and MUST NOT forward unrelated host secrets.
- Runtime remains stdlib-only; no new third-party runtime dependency is added.
- All V0.3 source/path/gate tests and all V0.2 Skill/Prompt/Harness compatibility tests remain release gates.

## File Structure

- `wikiskill/runtime_bindings.py` — static trusted profile registry, runtime workspace registration/activation state, runtime identity/fingerprint, detached worktree materialization, Python JSON v1 binding, `BoundRuntimeSession` lifecycle.
- `wikiskill/core_adapter.py` — split candidate lifecycle into `seal_candidate`, sealed-only `accept_candidate`, and cleanup of candidate temp refs on rejection.
- `wikiskill/assets.py` — CoreDriver exposes seal/finalize hooks rather than a boolean runtime-bound shortcut.
- `wikiskill/gating.py` — optional runtime evidence attached to per-task trace metadata; no change to grading semantics.
- `wikiskill/harness.py` — resolve accepted runtime for ordinary inference, enforce baseline comparability, bind exact sealed candidate for held-out Core scoring, two-phase accept/state update, refresh accepted runtime between iterations.
- `wikiskill/cli.py` — operator runtime bind/activate/inspect/validate and active-runtime-aware `run-task`.
- `wikiskill/prompts.py` — proposer instructions explicitly state that runtime profile selection is trusted operator state and unavailable to proposals.
- `tests/test_runtime_bindings.py` — registry/config/identity/worktree/Python protocol/security tests.
- `tests/test_v031_core_sealing.py` — exact candidate seal/temp-ref/accept/reject lifecycle tests.
- `tests/test_v031_runtime_integration.py` — harness baseline, causal candidate held-out, next-iteration accepted runtime, state compensation, framework-runner compatibility.
- `docs/V0.3.1-RUNTIME-BINDING.md`, `README.md`, `docs/index.md` — operator and causal-proof documentation.

- [ ] **Step 7: Implement two-phase source/state finalization with compensation**

On strict improvement:

1. bound candidate session must be closed successfully;
2. `driver.accept()` advances source accepted ref/state and returns old/new SHA;
3. persist `state.r_best` and new `runtime_identity` together through `gating.save_state()`;
4. if state save raises, attempt `sources.advance_accepted_sha(ws, source_id, new_sha, old_sha, recovery_iteration)` or a dedicated compare-and-swap compensation helper that updates accepted ref/state back to old SHA;
5. if compensation succeeds, record operational error with old runtime identity/R_best;
6. if compensation cannot be proven, preserve a recovery ref/evidence and raise operational error rather than claiming acceptance.

Do not delete recovery evidence before both source state and scoring state are confirmed.
