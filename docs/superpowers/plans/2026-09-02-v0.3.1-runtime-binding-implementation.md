# WikiSkill-Evolution V0.3.1 Trusted Runtime Binding Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Close the V0.3 causal gap by binding accepted and candidate Core source SHAs to trusted executable runtimes so baseline/train/held-out scores are produced by the exact source commit recorded in runtime evidence.

**Architecture:** Add a static trusted runtime-binding registry plus explicit workspace runtime registration/activation. Split Core finalization into seal → bind → held-out score → source transition → score-state commit → recovery-ref release. Ordinary inference uses detached accepted-runtime worktrees resolved from the authoritative accepted ref; Core candidate held-out uses the exact sealed candidate worktree. The first concrete profile is a fixed Python JSON protocol with no proposal-supplied argv, entrypoint, timeout, environment, credentials, or runtime commands.

**Tech Stack:** Python 3.10+, Python stdlib only, Git CLI subprocesses, pytest, pyflakes, GitHub Actions Python 3.10/3.11/3.12 matrix.

**Spec:** `docs/superpowers/specs/2026-09-02-v0.3.1-runtime-binding-design.md`

## Global Constraints

- Base is `feature/v0.3-git-source-adapter@6ecea640d0d91217f4239f9f50a13030ea492cb2`; PR #3 receives no V0.3.1 commits.
- Proposal JSON remains untrusted source-edit data and MUST NOT contain runtime profile ids, argv, entrypoints, environment variables, credentials, ports, device ids, executable paths, timeouts, or runtime commands.
- Runtime binding registration and activation are explicit operator actions only; V0.3.1 has one active role: `inference`.
- Activation is allowed only while `state.baseline is None`; no silent re-baselining.
- Accepted runtime authority is always a host-generated detached Git worktree at `refs/wikiskill/<source_id>/accepted`, never the source repository's current checkout.
- Candidate runtime binding requires a sealed immutable candidate commit plus `refs/wikiskill/<source_id>/candidate-<iteration>`.
- A boolean is never binding evidence. Held-out execution requires a `BoundRuntimeSession` whose verified `source_sha` equals the exact accepted/candidate SHA.
- Baseline, train, and held-out for Skill/Prompt/Harness candidates use the active accepted runtime when configured. Core candidate held-out uses the bound sealed candidate runtime. Maintainer/Proposer always use the framework/backend runner.
- Accepted runtime is re-resolved at each rollout phase that may follow Core acceptance; it is not cached for an entire multi-iteration evolve call.
- Candidate held-out MUST NOT fall back to accepted/default runner.
- Core acceptance transaction is: close candidate binding → remove candidate worktree → source CAS A→B while keeping candidate ref → atomically persist `R_best/runtime_identity/history` → delete candidate ref → Wiki audit.
- If score-state persistence fails after source CAS, compensate source CAS B→A. Compensation failure produces `recovery_required`, preserves candidate ref, and blocks later scoring on identity/ref mismatch.
- `R_best` and `state.runtime_identity` advance only after source transition succeeds and score state is durably written.
- Python proof profile uses a minimal environment and MUST NOT forward unrelated host secrets.
- Runtime remains stdlib-only. All V0.3 source/path/gate and V0.2 Skill/Prompt/Harness tests remain release gates.
