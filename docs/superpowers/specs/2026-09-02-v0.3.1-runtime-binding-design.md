# WikiSkill-Evolution V0.3.1 — Trusted Candidate Runtime Binding

Date: 2026-09-02
Status: Design approved in chat; implementation not started
Base: `feature/v0.3-git-source-adapter@6ecea640d0d91217f4239f9f50a13030ea492cb2`
Predecessor: V0.3 Governed Git Source Adapter

## 1. Problem

V0.3 proves that a Core proposal can mutate a pre-registered Git source safely in an isolated worktree, run trusted Static/Build/Regression/Performance engineering gates, and fail closed when infrastructure is unsafe.

Final review exposed a causal gap: the ordinary WikiSkill held-out runner does not automatically execute the candidate source in that worktree. Therefore engineering-gate success alone cannot justify `R_candidate > R_best`. V0.3 correctly fails closed before held-out scoring when the candidate runtime is not bound.

V0.3.1 closes that gap. A Core candidate may reach held-out scoring only through a **trusted runtime binding** that proves which exact candidate commit produced the task execution. If no trusted binding exists, the V0.3 fail-closed behavior remains.

The target closed loop is:

```text
accepted source SHA + trusted runtime binding
        ↓
normal train/baseline tasks execute accepted runtime
        ↓
WikiSkill proposes bounded Core patch
        ↓
isolated worktree + engineering gates
        ↓
seal exact candidate commit + temporary reachability ref
        ↓
trusted candidate runtime binding
        ↓
held-out tasks execute candidate runtime
        ↓
R_candidate > R_best ?
   YES → close binding → cleanup worktree → accepted-ref CAS → R_best advance
   NO  → close binding → cleanup worktree/temp ref → accepted ref unchanged
        ↓
subsequent train/val runs resolve the newly accepted runtime
```

## 2. Architectural decision

Use a **Trusted Runtime Binding Registry** separate from proposal data.

The trust model becomes:

```text
Source Registry            = trusted repository/path/gate policy
Runtime Binding Registry   = trusted execution adapter definitions
Workspace Runtime Config   = explicit operator choice of active inference source
Core Proposal              = untrusted bounded source edits
Runtime Binding Session    = evidence-bearing execution boundary
```

The proposal cannot choose a binding, runtime command, environment variables, credentials, entrypoint, device, port, executable path, or protocol. It can only choose a previously registered `source_id` and a bounded source patch as in V0.3.

V0.3.1 does not weaken any V0.3 source/path/Git/Gate safety rule.

## 3. Scope

V0.3.1 implements:

- a static trusted runtime-binding profile registry;
- explicit operator registration/activation of one inference runtime source;
- exact candidate sealing before held-out execution;
- a bound runner contract compatible with `gating.run_gate()`;
- persistent accepted-runtime resolution for normal train/baseline/val task execution;
- causal runtime evidence in traces/history/Wiki;
- one concrete automated binding: a fixed-protocol Python JSON runner;
- fail-closed behavior for missing/invalid bindings;
- tests proving that candidate source changes, not the old runner, cause held-out score changes.

## 4. Non-goals

V0.3.1 will not:

- add llama.cpp/CMake-specific runtime logic;
- add Android/Gradle/NDK/APK installation;
- use ADB or Shizuku;
- add phone thermal/power gates;
- allow proposal-supplied shell commands or runtime configuration;
- dynamically register binding profiles from proposals;
- support multiple simultaneously active inference runtimes;
- automatically activate a runtime source on behalf of the proposer;
- provide a hostile-code security sandbox or network namespace;
- change model weights or binary patch policy;
- auto-open or merge cross-repository PRs.

The first release proves the causal binding architecture with a deterministic Python protocol. llama.cpp and Android become source-specific profiles on top of the same interface later.

## 5. Runtime configuration layout

V0.3 source manifests remain unchanged. Runtime configuration is kept separately so V0.3 manifests stay backward compatible and remain the source-policy authority.

```text
<workspace>/runtime/
├─ registrations.json
└─ active.json
```

`registrations.json` is explicit operator-authored state:

```json
{
  "version": 1,
  "sources": {
    "demo-core": {
      "binding_profile": "registered:python-json-runner-v1",
      "role": "inference"
    }
  }
}
```

`active.json` names the single active inference source:

```json
{
  "version": 1,
  "role": "inference",
  "source_id": "demo-core",
  "binding_profile": "registered:python-json-runner-v1"
}
```

The Evolution Proposer cannot write either file through a Core proposal.

## 6. Operator CLI

V0.3.1 adds only explicit operator commands:

```text
wikiskill runtime bind <source_id> <binding_profile> [--ws PATH]
wikiskill runtime activate <source_id> [--ws PATH]
wikiskill runtime inspect [--ws PATH]
wikiskill runtime validate [--ws PATH]
```

There is intentionally no:

```text
wikiskill runtime exec ...
wikiskill runtime register-command ...
```

Rules:

1. `runtime bind` requires the source to exist in the trusted Source Registry and the profile to exist in the static Runtime Binding Registry.
2. `runtime activate` requires an existing valid runtime registration.
3. V0.3.1 activation is allowed only before the workspace has a scored baseline (`state.baseline is None`). If a baseline already exists, activation fails closed and tells the operator to use a fresh/reset scoring workspace. Silent re-baselining is not allowed in V0.3.1.
4. After Core acceptance, changing only the accepted SHA does not require reactivation. The same active source/profile automatically resolves the newly accepted commit.

## 7. Trusted Runtime Binding Registry

Create `wikiskill/runtime_bindings.py`.

The production registry is static code, analogous to `wikiskill/gates.py`.

Conceptual interface:

```python
@dataclass(frozen=True)
class RuntimeBindingProfile:
    profile_id: str
    protocol: str
    timeout_s: int
    entrypoint: str | None = None

PROFILES: dict[str, RuntimeBindingProfile]
```

Production V0.3.1 initially contains:

```text
registered:python-json-runner-v1
```

Tests may inject test profiles through an explicit dependency seam. Production runtime CLI cannot add or redefine profile code.

Profiles are resolved only from trusted workspace runtime registration; proposal JSON never carries a profile id.

## 8. Runtime identity and evidence

Every accepted or candidate bound runtime receives an immutable identity:

```text
source_id
binding_profile
source_sha
protocol_version
```

A canonical SHA-256 fingerprint is computed over those fields.

For the Python binding, evidence also includes:

- exact candidate/accepted Git commit SHA;
- worktree HEAD readback;
- fixed entrypoint relative path;
- Git blob SHA of the entrypoint at that commit;
- binding profile id;
- runtime fingerprint;
- bounded launch metadata with no secret values;
- request count and per-task runtime fingerprint in trace metadata.

A boolean such as `candidate_runtime_bound=True` is not sufficient evidence in V0.3.1. The harness must possess a `BoundRuntimeSession` produced by the trusted registry for the exact candidate SHA.

## 9. Candidate sealing lifecycle

V0.3 currently creates the candidate commit during final acceptance. V0.3.1 moves candidate commit creation earlier because runtime binding must execute an exact immutable candidate identity.

Add a sealing phase after engineering gates pass:

```text
apply bounded edits
    ↓
Static / Build / Regression / optional Performance
    ↓
verify tracked diff integrity again
    ↓
stage only expected changed source files
    ↓
commit detached candidate
    ↓
create refs/wikiskill/<source_id>/candidate-<iteration>
    ↓
record candidate_sha
    ↓
keep worktree alive for runtime binding
```

Proposed adapter split:

```python
seal_candidate(session, iteration) -> dict
accept_candidate(session, iteration) -> dict
reject_candidate(session) -> dict
```

`seal_candidate()` never advances the accepted ref.

`accept_candidate()` requires a sealed candidate. It no longer creates the candidate commit. After held-out success it:

1. closes the runtime binding;
2. removes the candidate worktree successfully;
3. compare-and-swap advances `refs/wikiskill/<source_id>/accepted` from `base_sha` to `candidate_sha`;
4. updates the accepted-state JSON mirror;
5. removes the temporary candidate ref;
6. returns accepted SHA evidence.

If cleanup fails, the accepted ref must remain unchanged.

If accepted-ref CAS fails after cleanup, the temporary candidate ref remains for diagnosis/recovery and `R_best` remains unchanged.

`reject_candidate()` removes the worktree and temporary candidate ref when safe; the accepted ref is never changed.

## 10. BoundRuntimeSession contract

A successful binding creates a host-owned session conceptually equivalent to:

```python
@dataclass
class BoundRuntimeSession:
    source_id: str
    source_sha: str
    profile_id: str
    fingerprint: str
    runner: Callable
    evidence: dict
    close: Callable[[], dict]
```

The runner must match the existing agent-runner call shape consumed by `gating.run_task()`:

```text
runner(ws, prompt, *, tag, workdir=None, model=None,
       dry_run=False, max_turns=..., **kwargs) -> dict
```

The harness does not construct this runner itself. It requests it from the trusted binding registry for an exact source SHA/worktree.

`close()` is mandatory and idempotent. A close failure is operational and prevents acceptance.

## 11. Persistent active runtime resolution

Core evolution is not complete if the candidate is used only during acceptance and then normal training returns to the old runner.

Therefore V0.3.1 resolves the active accepted runtime for ordinary task rollouts:

```text
workspace runtime/active.json
      ↓
source_id + trusted binding profile
      ↓
Source Registry accepted SHA
      ↓
materialize/bind accepted runtime
      ↓
train/baseline/val task runner
```

Only **task inference rollouts** use the active runtime binding. Wiki maintainer and Evolution Proposer turns continue to use the framework/backend runner unless a later design explicitly changes them.

`harness.evolve()` resolves the active accepted runtime once for the ordinary train/baseline task path and closes it safely after the evolution call. CLI `run-task` uses the same active-runtime resolution.

Direct low-level tests may inject an explicit runner and bypass runtime resolution through a documented test seam.

## 12. Score comparability rule

A Core candidate score is meaningful only if `R_best` was produced by the currently active accepted runtime under the same binding role.

V0.3.1 therefore requires runtime activation **before initial baseline scoring**.

At baseline creation, state records:

```json
{
  "runtime_identity": {
    "source_id": "demo-core",
    "binding_profile": "registered:python-json-runner-v1",
    "accepted_sha": "...",
    "fingerprint": "..."
  }
}
```

Before every evolve call, the harness checks:

- active source id/profile equal the recorded runtime identity;
- the recorded accepted SHA equals the current accepted ref, except when the same iteration is about to advance it through successful Core acceptance.

Initial activation after a scored baseline is rejected in V0.3.1 rather than silently comparing incompatible scores.

On successful Core acceptance, the harness updates `R_best` to `R_candidate` and atomically updates `state.runtime_identity` to the newly accepted SHA/fingerprint after source acceptance succeeds.

On rejection or operational failure, both remain unchanged.

## 13. Candidate held-out data flow

For an active runtime source Core proposal:

```text
current accepted runtime already owns R_best
        ↓
apply + engineering gates
        ↓
seal candidate_sha
        ↓
trusted runtime binding(candidate_sha)
        ↓
verify binding evidence source_sha == candidate_sha
        ↓
gating.run_gate(..., runner=bound_candidate.runner,
                 runtime_evidence=bound_candidate.evidence)
        ↓
R_candidate
        ↓
strict comparison with current R_best
```

The ordinary accepted-runtime runner must not be called for candidate held-out tasks.

If the proposal targets a source that is not the active inference source, V0.3.1 rejects it as invalid for capability scoring. Multi-source dependency graphs are deferred.

## 14. Python JSON Runner v1

The first concrete profile proves the interface without tying V0.3.1 to llama.cpp or Android.

Profile id:

```text
registered:python-json-runner-v1
```

Fixed protocol:

- trusted entrypoint relative path: `wikiskill_runtime.py`;
- process: host `sys.executable` runs that exact file from the bound source worktree;
- `cwd`: candidate/accepted source worktree;
- `shell=False`;
- request: one JSON object over stdin;
- response: one JSON object over stdout;
- timeout: fixed by trusted profile;
- proposal cannot alter entrypoint, argv, timeout, protocol, or environment policy.

Request fields are bounded and include only what the runner needs:

```json
{
  "protocol": "wikiskill-runtime-v1",
  "prompt": "...",
  "tag": "iter-01/val/task-1",
  "workdir": "/resolved/task/sandbox",
  "max_turns": 15
}
```

The candidate runtime writes task outputs into the supplied task sandbox. The host, not candidate JSON, owns trace/evidence file locations.

The response contract is intentionally small:

```json
{
  "status": "ok"
}
```

The host records process exit code, duration, bounded stdout/stderr, and runtime identity. Candidate-supplied arbitrary file paths are ignored.

Environment policy is fixed by the profile. V0.3.1 Python proof binding passes a minimal environment and does not forward arbitrary workspace/model credentials. Future source-specific profiles may explicitly allow named credential variables under a separate design.

This profile provides process isolation from the host Python interpreter but is **not** a hostile-code sandbox and does not promise network isolation.

## 15. Trace and audit integration

Extend task trace metadata with an optional bounded runtime block:

```json
{
  "runtime": {
    "source_id": "demo-core",
    "source_sha": "...",
    "binding_profile": "registered:python-json-runner-v1",
    "fingerprint": "sha256:..."
  }
}
```

Core history/Wiki evidence includes:

- base accepted runtime identity;
- candidate source SHA;
- runtime binding profile;
- candidate runtime fingerprint;
- binding validation result;
- held-out score;
- close/cleanup result;
- accepted ref transition or rejection reason.

The full binding command/env is not logged if it could expose sensitive values. V0.3.1 proof profile has no secret env values.

## 16. Failure classes

### Invalid candidate/configuration

Examples:

- Core proposal targets non-active source;
- runtime source is not bound to a trusted profile;
- active runtime config references unknown source/profile;
- activation attempted after scoring already exists;
- Python profile entrypoint missing at the bound SHA.

Behavior: fail closed before held-out scoring; no accepted-ref or `R_best` change.

### Candidate quality rejection

Examples:

- engineering gate fail;
- candidate bound runtime executes correctly but `R_candidate <= R_best`.

Behavior: reject candidate, close binding, cleanup candidate worktree/temp ref, preserve Wiki evidence.

### Operational failure

Examples:

- binding process cannot launch;
- timeout;
- invalid runtime JSON response;
- bound source SHA/worktree HEAD mismatch;
- binding close fails;
- cleanup/CAS failure.

Behavior: `operational_error`; never advance accepted ref or `R_best`; preserve recovery evidence.

## 17. Security invariants

V0.3.1 must preserve:

- proposal remains data, not runtime configuration;
- source registration remains operator-only;
- runtime binding/activation remains operator-only;
- binding profile code/argv/entrypoint/env policy come only from static trusted registry;
- exact source SHA is verified before any bound held-out task;
- candidate is sealed to an immutable commit before runtime binding;
- candidate held-out tasks cannot silently fall back to the accepted/default runner;
- binding evidence is attached to each task trace;
- missing evidence is fail-closed;
- accepted ref advances only after held-out improvement and successful binding close/worktree cleanup;
- `R_best` advances only after accepted-ref advancement succeeds;
- framework maintainer/proposer roles are not accidentally switched to candidate runtime;
- no arbitrary runtime CLI exec surface exists.

## 18. Test-first release gates

### Registry/configuration

1. unknown binding profile rejected;
2. unknown source rejected;
3. runtime binding is operator state, not proposal-controlled;
4. only one active inference source allowed;
5. activation before baseline succeeds;
6. activation after existing scored baseline fails closed;
7. runtime inspect/validate returns source/profile/accepted SHA without secrets.

### Candidate sealing

8. candidate is committed after engineering gates and before binding;
9. temporary candidate ref keeps candidate commit reachable;
10. sealing stages only expected source files;
11. sealing does not advance accepted ref;
12. rejection removes candidate worktree/temp ref and leaves accepted ref unchanged;
13. acceptance uses already sealed SHA and does not create a second candidate commit.

### Binding safety

14. unbound Core candidate cannot reach held-out scoring;
15. bound session source SHA must equal sealed candidate SHA;
16. worktree HEAD mismatch fails closed;
17. missing Python entrypoint fails closed;
18. Python runtime invalid JSON is operational failure;
19. Python runtime timeout is operational failure;
20. candidate cannot supply argv/entrypoint/env/timeout;
21. proof profile does not forward an unrelated secret environment variable;
22. binding close is idempotent;
23. close failure prevents acceptance.

### Causal execution

24. accepted Python runtime produces baseline score through its own source code;
25. candidate patch changes `wikiskill_runtime.py` behavior;
26. candidate held-out gate calls bound candidate runner and not the accepted/default runner;
27. per-task trace runtime SHA equals candidate SHA;
28. candidate improvement accepts and advances ref;
29. candidate non-improvement rejects and does not advance ref;
30. after acceptance, a subsequent train task resolves and executes the newly accepted runtime SHA;
31. `state.runtime_identity` advances only after source acceptance succeeds;
32. operational failure leaves `state.runtime_identity` and `R_best` unchanged.

### Compatibility

33. V0.3 source/path/gate tests remain green;
34. V0.2 Skill/Prompt/Harness behavior remains green;
35. workspaces with no active runtime keep legacy runner behavior;
36. maintainer/proposer still use framework/backend runner;
37. Python 3.10/3.11/3.12 CI remains green;
38. pyflakes remains zero.

## 19. End-to-end acceptance proof

V0.3.1 is complete only when an automated real-Git fixture proves this exact causal loop:

```text
register source at SHA A
bind registered:python-json-runner-v1
activate source before baseline
        ↓
accepted SHA A runtime writes a failing held-out answer
baseline/R_best recorded with SHA A runtime evidence
        ↓
Core proposal edits wikiskill_runtime.py in isolated worktree
engineering gates pass
candidate sealed as SHA B
        ↓
trusted Python binding launches SHA B entrypoint
candidate held-out task now passes
trace proves source_sha == SHA B
        ↓
R_B > R_best
binding closes
worktree cleanup succeeds
accepted ref CAS A → B
state.runtime_identity A → B
R_best advances
        ↓
next train rollout resolves accepted SHA B
and executes SHA B runtime without special candidate override
```

A test that merely sets a fake `candidate_runtime_bound=True` flag is not sufficient release evidence.

## 20. V0.3.2 / V0.4 handoff

After the Python causal proof is stable, the same registry/session contract can add trusted profiles such as:

```text
registered:llama-cpp-cli-v1
registered:android-local-runtime-v1
```

Those profiles may add source-specific build artifacts, model invocation, device routing, TTFT/decode/memory metrics, thermal/power gates, or ADB/Shizuku orchestration only through separately approved designs. They must not bypass V0.3.1 candidate sealing, runtime identity, trace evidence, strict held-out improvement, cleanup, and accepted-ref CAS semantics.
