# WikiSkill-Evolution V0.3.1 — Trusted Candidate Runtime Binding

Date: 2026-09-02
Status: Design approved in chat; implementation not started
Base: `feature/v0.3-git-source-adapter@6ecea640d0d91217f4239f9f50a13030ea492cb2`
Predecessor: V0.3 Governed Git Source Adapter

## 1. Problem

V0.3 proves that a Core proposal can safely mutate a pre-registered Git source in an isolated worktree and pass trusted Static/Build/Regression/Performance engineering gates. Final review exposed a causal gap: the ordinary WikiSkill held-out runner does not automatically execute that candidate source.

V0.3 therefore correctly fails closed before Core held-out scoring when a candidate runtime is not causally bound. V0.3.1 closes that gap.

A Core candidate may reach held-out scoring only through a **trusted runtime binding** that proves which exact source commit produced task execution. The accepted runtime must also be used for ordinary baseline/train/val rollouts so a newly accepted Core remains active in later iterations.

Target loop:

```text
trusted active runtime configuration
        ↓
accepted source SHA → accepted runtime binding
        ↓
baseline/train tasks execute accepted runtime
        ↓
WikiSkill proposes bounded Core patch
        ↓
isolated candidate worktree + engineering gates
        ↓
seal exact candidate commit + temporary candidate ref
        ↓
trusted candidate runtime binding
        ↓
held-out tasks execute candidate runtime
        ↓
R_candidate > R_best ?
   YES → close binding → cleanup worktree → accepted-ref CAS
          → score/runtime-state commit → remove temp ref
   NO  → close binding → cleanup worktree/temp ref
        ↓
next rollout resolves accepted ref again
```

## 2. Architectural decision

Use a **Trusted Runtime Binding Registry** separate from proposal data.

```text
Source Registry            = trusted repository/path/gate policy
Runtime Binding Registry   = trusted execution adapter definitions
Workspace Runtime Config   = explicit operator choice of active inference source
Core Proposal              = untrusted bounded source edits
BoundRuntimeSession        = evidence-bearing execution boundary
```

The proposal cannot choose a binding, command, environment, credential, entrypoint, device, port, executable, timeout, or protocol. It can only choose a registered `source_id` plus V0.3 bounded edits.

A boolean such as `candidate_runtime_bound=True` is no longer sufficient proof. Held-out scoring requires a `BoundRuntimeSession` produced by the trusted registry for the exact sealed candidate SHA.

## 3. Scope

V0.3.1 implements:

- static trusted runtime-binding profiles;
- operator-only binding and activation of one inference source;
- accepted-runtime execution for normal task rollouts;
- immutable candidate sealing before binding;
- a bound runner compatible with `gating.run_gate()`;
- causal runtime evidence in task traces/history/Wiki;
- one real automated profile: `registered:python-json-runner-v1`;
- two-phase acceptance across source ref and WikiSkill score/runtime state;
- fail-closed handling for missing binding, stale runtime identity, close/cleanup/CAS/state failures;
- end-to-end tests proving that source code at candidate SHA, not the old/default runner, causes the score change.

## 4. Non-goals

V0.3.1 does not add:

- llama.cpp/CMake-specific runtime logic;
- Android/Gradle/NDK/APK installation;
- ADB/Shizuku or phone thermal/power gates;
- proposal-supplied shell/runtime configuration;
- dynamic profile registration by an agent;
- multiple simultaneously active inference runtimes;
- automatic runtime activation by the proposer;
- model-weight/binary mutation;
- hostile-code/network sandbox guarantees;
- cross-repository PR/merge automation.

The first release proves the causal runtime architecture with a deterministic Python subprocess protocol. Source-specific llama.cpp/Android profiles come later without changing the lifecycle.

## 5. Runtime configuration

V0.3 source manifests remain unchanged. Runtime configuration is separate trusted operator state:

```text
<workspace>/runtime/
├─ registrations.json
└─ active.json
```

`registrations.json`:

```json
{
  "version": 1,
  "sources": {
    "demo-core": {
      "binding_profile": "registered:python-json-runner-v1",
      "role": "inference"
    }
  }
}
```

`active.json`:

```json
{
  "version": 1,
  "role": "inference",
  "source_id": "demo-core",
  "binding_profile": "registered:python-json-runner-v1"
}
```

The Evolution Proposer cannot mutate these files through a Core proposal.

## 6. Operator CLI

V0.3.1 adds:

```text
wikiskill runtime bind <source_id> <binding_profile> [--ws PATH]
wikiskill runtime activate <source_id> [--ws PATH]
wikiskill runtime inspect [--ws PATH]
wikiskill runtime validate [--ws PATH]
```

There is intentionally no generic `runtime exec` or `runtime register-command` surface.

Rules:

1. `bind` requires an existing trusted source and a profile present in the static Runtime Binding Registry.
2. `activate` requires a valid binding registration.
3. Only one active `inference` source exists in V0.3.1.
4. Initial activation is allowed only while `gating.state.baseline is None`. If scoring already exists, activation fails closed instead of silently comparing incompatible runtimes. The operator must use a fresh/reset scoring workspace.
5. Core acceptance changes only the accepted SHA behind the same active source/profile, so no reactivation is needed.

## 7. Trusted Runtime Binding Registry

Create `wikiskill/runtime_bindings.py`.

Production profiles are static code analogous to `wikiskill/gates.py`:

```python
@dataclass(frozen=True)
class RuntimeBindingProfile:
    profile_id: str
    protocol: str
    timeout_s: int
    entrypoint: str | None = None
```

Initial production profile:

```text
registered:python-json-runner-v1
```

Tests may inject profiles through an explicit dependency seam. Production CLI/proposal data cannot add or redefine profile behavior.

## 8. Runtime identity

Every accepted/candidate binding has an immutable identity:

```text
source_id
binding_profile
source_sha
protocol_version
```

A canonical SHA-256 fingerprint is computed from those fields.

Binding evidence must include at least:

- `source_id`;
- exact accepted/candidate Git SHA;
- binding profile;
- runtime fingerprint;
- bound worktree HEAD readback;
- protocol version;
- bounded profile-specific evidence.

For the Python profile also record the fixed entrypoint and its Git blob SHA at the bound commit.

Each task trace carries the same bounded runtime identity so the held-out score can be tied to the source SHA that actually ran.

## 9. Accepted runtime materialization

The registered source repository's current working tree is **never** treated as accepted runtime authority. It may be on another branch or have unrelated local state.

For normal task rollouts V0.3.1 creates a host-generated detached runtime worktree at the exact authoritative accepted ref SHA:

```text
<workspace>/runs/runtime-worktrees/
  accepted-<source_id>-<short-sha>-<host-generated-id>/
```

Rules:

- the path is generated by WikiSkill, never proposal/config input;
- `git worktree add --detach <path> <accepted_sha>` materializes the exact runtime source;
- bound worktree `HEAD` must equal accepted SHA before the first task;
- close removes/prunes the accepted runtime worktree;
- the source repository's normal working tree is never mutated;
- accepted commit reachability is already guaranteed by `refs/wikiskill/<source_id>/accepted`.

Candidate binding uses the existing candidate worktree after candidate sealing; it does not create a second candidate checkout.

## 10. Candidate sealing

V0.3 currently creates the candidate commit during final acceptance. V0.3.1 moves commit creation before binding so held-out execution has an immutable source identity.

Pipeline:

```text
bounded edits
  ↓
Static → Build → Regression → optional Performance
  ↓
verify tracked diff integrity
  ↓
stage only expected source files
  ↓
commit detached candidate
  ↓
create refs/wikiskill/<source_id>/candidate-<iteration>
  ↓
record candidate_sha
  ↓
keep candidate worktree alive
```

Adapter split:

```python
seal_candidate(session, iteration) -> dict
advance_accepted_candidate(session, iteration) -> dict
compensate_accepted_candidate(transition) -> dict
release_candidate_ref(session) -> dict
reject_candidate(session) -> dict
```

`seal_candidate()` never changes the accepted ref.

`reject_candidate()` handles both unsealed and sealed candidates. For a sealed rejection it removes the candidate worktree and deletes the temporary candidate ref; the accepted ref remains unchanged.

`advance_accepted_candidate()` requires a sealed candidate and performs the accepted-ref/source-state CAS, but intentionally **keeps the temporary candidate ref** until WikiSkill score/runtime state is durably written.

`release_candidate_ref()` deletes that temporary ref only after the cross-state acceptance transaction is complete.

## 11. BoundRuntimeSession

A trusted binding returns a host-owned object conceptually equivalent to:

```python
@dataclass
class BoundRuntimeSession:
    source_id: str
    source_sha: str
    profile_id: str
    fingerprint: str
    runner: Callable
    evidence: dict
    close: Callable[[], dict]
```

`runner` matches the existing task-runner contract:

```text
runner(ws, prompt, *, tag, workdir=None, model=None,
       dry_run=False, max_turns=..., **kwargs) -> dict
```

The registry/binder creates the runner. Harness/proposal code does not manufacture or bless it.

`close()` is mandatory and idempotent. Close failure is operational and prevents source acceptance.

For accepted runtime sessions, close also removes the host-generated accepted runtime worktree. For candidate sessions, close releases binding-owned resources but leaves candidate worktree cleanup to `core_adapter`.

## 12. Runtime resolution in ordinary rollouts

Only **task inference rollouts** use the active runtime binding. Maintainer and Evolution Proposer turns continue to use the framework/backend runner.

The accepted runtime must be re-resolved at each rollout phase that can follow a Core acceptance; it is not cached for the entire multi-iteration `evolve()` call.

Required behavior:

```text
initial baseline phase
  → bind current accepted runtime → run val baseline → close

iteration N train phase
  → bind current accepted runtime → run train → close

iteration N Core candidate held-out
  → bind sealed candidate runtime → run val → close
  → accept/reject

iteration N+1 train phase
  → resolve accepted ref again
  → if N accepted Core, bind the new SHA
```

CLI `run-task` also resolves the active accepted runtime for that one task and closes it afterward.

Workspaces with no active runtime preserve legacy runner behavior.

Low-level tests retain an explicit runner/runtime-resolver injection seam.

## 13. Score comparability and runtime epoch

A Core candidate score is meaningful only when `R_best` was produced by the currently active accepted runtime under the same inference role.

Runtime activation must therefore happen before the initial baseline.

When baseline is created, gating state stores:

```json
{
  "runtime_identity": {
    "source_id": "demo-core",
    "binding_profile": "registered:python-json-runner-v1",
    "accepted_sha": "...",
    "fingerprint": "sha256:..."
  }
}
```

Before baseline/train/evolve, if runtime state exists the harness verifies:

- active source/profile match the recorded identity;
- current authoritative accepted ref matches recorded `accepted_sha`;
- fingerprint is recomputed from trusted config/ref and matches.

Any out-of-band accepted-ref/config change produces an operational mismatch and stops scoring. V0.3.1 does not silently rebaseline.

On successful Core acceptance, the new candidate score becomes `R_best` and runtime identity advances to the new accepted SHA/fingerprint as part of the two-phase transaction below.

## 14. Candidate held-out flow

A Core proposal may be capability-scored only when its `source_id` is the active inference source.

```text
current accepted runtime owns R_best
      ↓
Core patch + engineering gates
      ↓
seal candidate SHA B
      ↓
trusted bind candidate SHA B
      ↓
verify session.source_sha == B
verify candidate worktree HEAD == B
      ↓
gating.run_gate(...,
  runner=bound_candidate.runner,
  runtime_evidence=bound_candidate.evidence)
      ↓
R_candidate
```

The accepted/default task runner must not be invoked for candidate held-out tasks. Missing binding evidence or a SHA mismatch fails closed.

Non-active-source Core proposals are invalid for V0.3.1 capability evolution. Multi-source dependency graphs are deferred.

## 15. Two-phase acceptance transaction

A candidate with `R_candidate > R_best` is not yet accepted until runtime resources, source state, and WikiSkill score state all close safely.

Required sequence:

```text
1. close candidate BoundRuntimeSession successfully
2. remove/prune candidate worktree successfully
3. CAS accepted source ref/state A → B, keep candidate temp ref
4. prepare and atomically write gating state:
     R_best = R_candidate
     runtime_identity = identity(B)
     history = accepted outcome
5. release temporary candidate ref
6. commit Wiki audit outcome
```

If step 1 or 2 fails: accepted ref and `R_best` remain A/old.

If step 3 fails: `R_best` and runtime identity remain unchanged; candidate temp ref preserves B for diagnosis.

If step 4 fails after source CAS A→B: attempt compensating source CAS/state rollback B→A. If compensation succeeds, score/runtime state stays unchanged and the result is `operational_error`. If compensation also fails, mark `recovery_required`; preserve the temporary candidate ref and make subsequent scoring fail closed on runtime-identity/ref mismatch.

The candidate temporary ref is deleted only after the source ref and gating state agree on B.

This strengthens the V0.3 acceptance boundary; it avoids reporting an accepted Core whose persistent score/runtime state could not be committed.

## 16. Python JSON Runner v1

Profile:

```text
registered:python-json-runner-v1
```

Fixed trusted contract:

- entrypoint: `wikiskill_runtime.py`;
- executable: host `sys.executable`;
- `cwd`: exact accepted/candidate runtime worktree;
- `shell=False`;
- request: one bounded JSON object on stdin;
- response: one JSON object on stdout;
- timeout/environment policy fixed in profile;
- proposal cannot alter entrypoint/argv/env/timeout/protocol.

Request:

```json
{
  "protocol": "wikiskill-runtime-v1",
  "prompt": "...",
  "tag": "iter-01/val/task-1",
  "workdir": "/resolved/task/sandbox",
  "max_turns": 15
}
```

The runtime writes task output files into the host-provided task sandbox. Candidate JSON cannot select trace/evidence output locations.

Response:

```json
{"status": "ok"}
```

Host code records exit code, duration, bounded stdout/stderr and runtime evidence. Arbitrary candidate-supplied file references are ignored.

The proof profile uses a minimal environment and does not forward unrelated host/workspace/model credentials. It provides process isolation from the host interpreter but is **not** a hostile-code or network sandbox.

## 17. Trace/audit integration

Extend task trace metadata with optional runtime identity:

```json
{
  "runtime": {
    "source_id": "demo-core",
    "source_sha": "...",
    "binding_profile": "registered:python-json-runner-v1",
    "fingerprint": "sha256:..."
  }
}
```

Core Wiki/history evidence records:

- previous accepted runtime identity;
- candidate SHA;
- binding profile/fingerprint;
- binding validation;
- held-out score;
- runtime close result;
- worktree cleanup result;
- accepted-ref transition/compensation result;
- new runtime identity or rejection/operational reason.

Secrets and full environment values are never logged.

## 18. Failure classification

### Invalid configuration/candidate

Examples:

- unknown source/profile;
- Core proposal targets non-active source;
- activation attempted after scoring exists;
- profile entrypoint missing at bound SHA;
- proposal tries to supply runtime controls.

Behavior: fail closed before candidate held-out scoring; no accepted-ref or `R_best` change.

### Candidate quality rejection

Examples:

- engineering Gate fails;
- bound candidate executes correctly but `R_candidate <= R_best`.

Behavior: close binding, reject/cleanup candidate, accepted ref/runtime identity/`R_best` unchanged, Wiki evidence retained.

### Operational failure

Examples:

- runtime process launch/timeout/invalid response;
- bound SHA or worktree HEAD mismatch;
- close/cleanup failure;
- accepted-ref CAS failure;
- score/runtime state write failure.

Behavior: `operational_error`; never deliberately advance `R_best`; preserve candidate/recovery evidence.

### Recovery-required inconsistency

If source-ref compensation fails after a score-state write failure, accepted source ref and gating runtime identity may temporarily disagree. The system records `recovery_required` and **all further scoring fails closed** until an operator recovery path restores agreement. No automatic guess chooses which side is authoritative.

## 19. Security invariants

V0.3.1 must preserve all of these:

- proposal is data, not runtime configuration;
- source registration and runtime bind/activate are operator-only;
- binding code/argv/entrypoint/env/timeout come only from static trusted profiles;
- accepted/candidate source SHA is read back before the first bound task;
- source repository ordinary working tree is never used as runtime authority;
- candidate is sealed before binding;
- candidate held-out cannot silently fall back to accepted/default runner;
- each task trace carries the runtime identity that ran it;
- missing/mismatched evidence fails closed;
- maintainer/proposer remain on framework backend;
- accepted ref advances only after candidate runtime close and worktree cleanup;
- `R_best` advances only when source transition and runtime identity can be durably aligned;
- no arbitrary `runtime exec` surface exists.

## 20. Test-first release gates

### Runtime registry/config

1. unknown binding profile rejected;
2. unknown source rejected;
3. proposal cannot select binding/profile/runtime controls;
4. only one active inference source;
5. activation before baseline succeeds;
6. activation after scored baseline fails closed;
7. inspect/validate returns source/profile/accepted SHA without secrets;
8. workspace with no active runtime preserves legacy behavior.

### Accepted runtime materialization

9. accepted runtime uses a detached worktree at exact accepted SHA;
10. source repository ordinary working tree may be on another commit without affecting runtime;
11. accepted binding rejects worktree HEAD mismatch;
12. accepted runtime worktree is removed on close;
13. accepted runtime is re-resolved for each later train phase after Core acceptance.

### Candidate sealing

14. candidate is committed only after engineering Gates;
15. candidate temp ref preserves sealed commit;
16. sealing stages only expected source files;
17. sealing never advances accepted ref;
18. rejection cleans worktree/temp ref and leaves accepted ref unchanged;
19. acceptance uses the already sealed SHA and creates no second candidate commit.

### Binding safety

20. unbound Core candidate cannot reach held-out;
21. bound session source SHA must equal sealed candidate SHA;
22. candidate worktree HEAD mismatch fails closed;
23. missing Python entrypoint fails closed;
24. invalid JSON response is operational failure;
25. timeout/process launch failure is operational failure;
26. proof profile does not forward an unrelated secret env variable;
27. close is idempotent;
28. close failure prevents acceptance.

### Causal execution

29. accepted Python runtime code produces baseline/R_best;
30. candidate patch changes `wikiskill_runtime.py` behavior;
31. candidate held-out uses candidate bound runner, not accepted/default runner;
32. every candidate held-out trace reports candidate SHA;
33. improvement accepts and advances source ref;
34. non-improvement rejects with ref unchanged;
35. after acceptance, next train phase resolves and executes new accepted SHA;
36. maintainer/proposer still use framework/backend runner.

### Transaction/state safety

37. runtime identity is stored with baseline;
38. out-of-band accepted-ref mismatch fails closed;
39. `R_best/runtime_identity` update occurs only after source CAS;
40. score-state write failure triggers compensating source CAS B→A;
41. successful compensation preserves old `R_best/runtime_identity`;
42. compensation failure records `recovery_required` and blocks later scoring;
43. candidate temp ref is retained until source+score state agree;
44. candidate temp ref is released only after successful transaction.

### Compatibility/release

45. all V0.3 source/path/Gate tests stay green;
46. all V0.2 Skill/Prompt/Harness behavior stays green;
47. Python 3.10/3.11/3.12 CI green;
48. pyflakes zero;
49. no temporary runtime worktrees/workflows/scripts committed.

## 21. End-to-end acceptance proof

V0.3.1 is complete only when a real-Git automated fixture proves:

```text
register source SHA A
bind python-json profile
activate before baseline
        ↓
materialize accepted SHA A detached runtime worktree
SHA A runtime makes held-out fail
baseline/R_best trace proves SHA A
close accepted runtime worktree
        ↓
Core proposal patches wikiskill_runtime.py
engineering gates pass
seal candidate SHA B + temp ref
        ↓
bind exact candidate worktree HEAD B
SHA B runtime makes same held-out pass
trace proves source_sha=B
        ↓
R_B > R_best
close candidate binding
cleanup candidate worktree
CAS accepted A→B
atomically persist R_best + runtime_identity(B)
release temp ref
        ↓
next train phase materializes accepted SHA B afresh
and executes SHA B without a candidate override
```

A fake boolean binding flag or a test that never executes candidate source is not sufficient evidence.

## 22. Handoff

After this Python causal proof is stable, source-specific profiles can be added without changing the lifecycle, for example:

```text
registered:llama-cpp-cli-v1
registered:android-local-runtime-v1
```

Those later profiles may add compiled artifacts, model invocation, device routing, TTFT/decode/memory/thermal/power evidence, ADB/Shizuku, or credential allowlists only through separately approved designs. They must preserve V0.3.1 sealing, exact runtime identity, per-task evidence, strict held-out improvement, two-phase acceptance, cleanup, and fail-closed recovery semantics.
