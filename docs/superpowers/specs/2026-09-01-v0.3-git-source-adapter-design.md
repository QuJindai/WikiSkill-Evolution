# WikiSkill-Evolution V0.3 — Governed Git Source Adapter

Date: 2026-09-01
Status: Design approved in chat; implementation not started
Base: `main@7089b8b35254edc5d636461f003c6e4655535f2c`
Predecessor: V0.2 Asset-Driver Evolution Architecture

## 1. Goal

V0.3 upgrades the V0.2 `core` target from a fail-closed placeholder into a governed source-code evolution path for pre-registered Git repositories.

The target outcome is:

```text
raw traces / wiki
      ↓
Evolution Proposer
      ↓
Core Proposal
      ↓
Source Registry + Git Source Adapter
      ↓
isolated worktree
      ↓
Static Gate → Build Gate → Regression Gate → Performance Gate interface
      ↓
existing WikiSkill held-out Gate
      ↓
PASS + R_candidate > R_best → ACCEPT
otherwise → ROLLBACK
      ↓
full audit remains in Wiki
```

V0.3 is the first phase in which WikiSkill may safely propose and test text source-code mutations. It must not gain arbitrary repository access, arbitrary shell execution, model-weight mutation, binary patching, or direct device flashing.

## 2. Architectural decision

Use a **generic Git Source Adapter** rather than a llama.cpp-specific or Android-specific adapter.

The generic adapter becomes the reusable execution boundary for later source profiles such as:

- `llama-cpp-mobile`
- `android-harness`
- `mllm-core`

A later phase may add source-specific registered gate profiles, but V0.3 must not fork the candidate lifecycle per project.

The trust model is:

```text
Source Registry / registered gates = trusted configuration
Core Proposal                    = untrusted input
Git Source Adapter               = enforcement boundary
```

The Evolution Proposer may choose among already-registered `source_id` values and may propose bounded text edits. It may not register a source, change a gate command, widen a write policy, choose a repository URL, or execute shell code.

## 3. Non-goals

V0.3 will not:

- install APKs on phones;
- use ADB or Shizuku;
- enforce thermal or power gates on a physical phone;
- add llama.cpp-specific benchmark logic;
- add Android signing/release logic;
- modify model weights;
- patch binary files;
- accept proposal-supplied shell commands;
- allow an agent to register new sources or registered gate profiles;
- automatically open or merge cross-repository pull requests;
- make performance measurements mandatory for sources that have no configured benchmark;
- weaken the V0.2 strict held-out acceptance rule `R_candidate > R_best`.

These are deliberately deferred so source mutation, source isolation, and rollback can be proven independently from device/build/signing complexity.

## 4. Source Registry

### 4.1 Workspace layout

V0.3 adds a trusted source registry under the workspace:

```text
workspaces/<domain>/
├─ sources/
│  ├─ registry.json
│  └─ manifests/
│     ├─ llama-cpp-mobile.json
│     ├─ android-harness.json
│     └─ mllm-core.json
├─ assets/
│  └─ core/
├─ raw/
├─ runs/
└─ wiki/
```

`registry.json` maps stable `source_id` values to manifest files. The Evolution Proposer receives readable source summaries but may not mutate registry or manifest files through a proposal.

### 4.2 Source manifest schema

A source manifest describes one trusted source repository and its immutable execution policy.

Example:

```json
{
  "source_id": "llama-cpp-mobile",
  "adapter": "git_source",
  "repository": "/trusted/path/or/resolved-repository-reference",
  "baseline_ref": "main",
  "baseline_sha": "LOCKED_FULL_COMMIT_SHA",
  "write_policy": {
    "allow": ["src/**", "common/**"],
    "deny": [".git/**", ".github/**", "secrets/**", "models/**"]
  },
  "patch_policy": {
    "max_files": 8,
    "max_total_lines": 500,
    "text_only": true
  },
  "gates": {
    "static": "registered:llama-static",
    "build": "registered:llama-build",
    "regression": "registered:llama-regression",
    "performance": null
  }
}
```

Required fields:

- `source_id`: stable simple identifier.
- `adapter`: exactly `git_source` in V0.3.
- `repository`: trusted pre-resolved repository location/reference.
- `baseline_ref`: human-readable accepted branch/ref.
- `baseline_sha`: full accepted Git commit SHA.
- `write_policy.allow`: non-empty glob allowlist.
- `write_policy.deny`: zero or more deny globs; deny always wins.
- `patch_policy.max_files`: positive bounded integer.
- `patch_policy.max_total_lines`: positive bounded integer.
- `patch_policy.text_only`: must be `true` in V0.3.
- `gates.static`, `gates.build`, `gates.regression`: registered gate identifiers.
- `gates.performance`: registered identifier or `null`.

Unknown manifest keys fail closed. V0.3 has no free-form metadata escape hatch in the manifest schema. Manifest validation occurs before a source can be registered or used.

### 4.3 Registry mutability

V0.3 CLI may register or inspect manifests under explicit operator control. The Evolution Proposer cannot call registration implicitly.

A registered source is trusted only after:

1. manifest schema passes;
2. repository resolves;
3. `baseline_sha` exists in that repository;
4. configured gate identifiers exist in the trusted gate registry;
5. allow/deny policies are internally valid.

## 5. Registered gate profiles

### 5.1 No proposal-supplied shell

A source manifest must not contain arbitrary shell strings such as:

```json
{"build": "cmake ... && rm -rf ..."}
```

Instead it references a pre-registered gate profile:

```json
{"build": "registered:llama-build"}
```

The registered gate profile is trusted configuration controlled outside the proposal path.

In V0.3, production gate profiles are a static trusted registry implemented in `wikiskill/gates.py`. There is no runtime or CLI API for an agent to add, replace, or redefine a registered gate profile. Tests may inject test-only profiles through an explicit dependency seam, but production proposal data never becomes executable configuration.

### 5.2 Gate result contract

Every pre-gate returns a structured result equivalent to:

```json
{
  "gate": "build",
  "profile": "registered:llama-build",
  "status": "pass|fail|not_configured",
  "exit_code": 0,
  "duration_s": 12.4,
  "summary": "bounded human-readable summary",
  "evidence": {
    "artifact_refs": [],
    "metrics": {}
  }
}
```

The adapter/harness records the result but does not let the proposal rewrite it.

## 6. Core proposal contract

V0.3 upgrades the `core` proposal to exactly one executable action: bounded text `patch` against a registered source.

```json
{
  "target": "core",
  "action": "patch",
  "source_id": "llama-cpp-mobile",
  "base_sha": "LOCKED_FULL_COMMIT_SHA",
  "edits": [
    {
      "file": "src/example.cpp",
      "op": "replace",
      "target": "old exact text",
      "content": "new text"
    }
  ]
}
```

V0.3 does not support `core create`.

Allowed edit operations:

- `replace`
- `insert_after`
- `append`

Every edit is text-only. `replace` and `insert_after` require exact target text. Patch application is deterministic and fails closed if the expected target is absent or ambiguous under the selected operation semantics.

The proposal must not contain:

- repository/repository URL fields;
- branch/ref selection other than `base_sha` verification;
- shell/command/script fields;
- environment variables;
- credentials;
- gate definitions;
- signing keys;
- binary payloads;
- model weights.

Unknown top-level or edit-level executable/control fields are rejected.

## 7. Source and path validation

Before creating a worktree, the adapter validates:

1. `source_id` exists in the registry;
2. source manifest passes schema validation;
3. proposal `base_sha` equals the current authoritative `refs/wikiskill/<source_id>/accepted` SHA (initialized from manifest `baseline_sha` at first registration);
4. repository object database can resolve that accepted SHA;
5. every edited path is relative and normalized;
6. every path matches at least one allow rule;
7. no path matches any deny rule;
8. no path escapes by `..`, absolute path, symlink, submodule boundary, or realpath mismatch;
9. edited file count does not exceed `max_files`;
10. total changed line budget does not exceed `max_total_lines`;
11. all files are text under the V0.3 policy;
12. proposal contains no forbidden control fields.

`deny` wins over `allow` in every conflict.

No worktree or build step is created before these checks pass.

## 8. Isolated Git worktree lifecycle

Each core candidate runs in a fresh isolated Git worktree rooted at the exact current accepted SHA. The worktree path is generated by the adapter under `workspaces/<domain>/runs/core-worktrees/iter-<NN>-<source_id>-<short-sha>/`; proposal data cannot choose or escape this root.

Conceptually:

```text
registered source repository
        ↓ exact accepted ref SHA
create candidate worktree
        ↓
apply bounded edits
        ↓
collect deterministic diff
        ↓
run pre-gates
        ↓
run WikiSkill held-out gate
        ↓
ACCEPT → commit candidate and advance accepted source baseline
REJECT → remove worktree; accepted source baseline unchanged
```

The adapter must not mutate the registered source working tree directly.

The adapter records:

- source repository identity;
- `source_id`;
- `base_sha`;
- candidate worktree identifier/path (bounded audit form, not proposal-controlled);
- changed files;
- unified diff;
- candidate commit SHA if created;
- cleanup result.

Worktree cleanup is mandatory after rejection and after accepted state has been safely committed/read back.

## 9. Pre-gate pipeline

The V0.3 source pipeline is ordered and short-circuiting:

```text
Schema/Registry Validation
        ↓
Patch Safety Validation
        ↓
Static Gate
        ↓ PASS only
Build Gate
        ↓ PASS only
Regression Gate
        ↓ PASS only
Performance Gate (if configured)
        ↓ PASS or not_configured
WikiSkill Held-out Gate
```

### 9.1 Static Gate — hard gate

Static Gate is mandatory and may validate:

- actual diff remains inside allowlist;
- denylist is untouched;
- no binary/symlink/submodule mutation;
- syntax/lint/format checks through the registered profile;
- actual changed-file and line budgets;
- proposal diff and observed Git diff agree on file scope.

Failure stops the pipeline before Build.

### 9.2 Build Gate — hard gate

Build Gate is mandatory. It uses only the source manifest's registered build profile.

The Evolution Proposer cannot select or alter build commands.

Failure stops the pipeline before Regression.

### 9.3 Regression Gate — hard gate

Regression Gate is mandatory and verifies existing behavior. Registered profiles may include:

- unit tests;
- regression tests;
- previously fixed bug reproductions;
- compatibility checks.

Failure rejects the candidate before the held-out task Gate.

### 9.4 Performance Gate — interface in V0.3

Performance Gate is implemented as a structured interface but may be `not_configured` for a source.

If configured, a profile may report metrics such as:

- decode tokens/s;
- TTFT;
- peak memory;
- latency;
- other source-specific metrics.

A configured performance profile may define regression tolerances in trusted configuration. The proposal cannot alter those thresholds.

V0.3 accepts `not_configured` only when the source manifest explicitly has no performance profile. A configured performance profile that returns `fail` is a hard rejection.

## 10. WikiSkill held-out Gate

Passing source-engineering gates is necessary but not sufficient.

The existing V0.2 validation rule remains unchanged:

```text
accept only if R_candidate > R_best
```

A candidate that compiles, passes regression, and has acceptable performance but does not strictly improve held-out task score is rejected and rolled back.

This preserves the distinction:

- pre-gates answer: “is this source patch safe and technically acceptable?”
- WikiSkill held-out Gate answers: “does this patch improve agent capability on held-out tasks?”

## 11. Acceptance and baseline advancement

On full acceptance:

1. candidate source worktree has a deterministic diff;
2. mandatory pre-gates pass;
3. performance is `pass` or explicitly `not_configured`;
4. held-out `R_candidate > R_best`;
5. candidate commit is created/read back;
6. the adapter atomically advances `refs/wikiskill/<source_id>/accepted` from the expected old accepted SHA to the candidate SHA using compare-and-swap semantics;
7. runtime accepted-source JSON mirrors that exact ref SHA;
8. WikiSkill `R_best` advances;
9. source/Wiki audit records are committed;
10. temporary worktree is removed safely.

The namespaced Git ref is the authoritative accepted-source baseline after registration. Keeping the commit reachable by this ref prevents a detached accepted commit from becoming garbage-collectable after worktree removal. The manifest remains the operator-authored initial anchor and policy document; runtime JSON is an audit/readability mirror, not the source of truth.

## 12. Rejection and rollback

Any of the following rejects the candidate:

- invalid proposal schema;
- unknown `source_id`;
- baseline mismatch;
- path/policy violation;
- patch application failure;
- Static Gate fail;
- Build Gate fail;
- Regression Gate fail;
- configured Performance Gate fail;
- held-out score not strictly better;
- inability to prove accepted candidate commit/readback.

On rejection:

- accepted source baseline remains unchanged;
- registered source working tree remains unchanged;
- candidate worktree is removed;
- Wiki remains unchanged except for appended audit/knowledge;
- the complete rejected proposal, actual diff if any, gate results, and rejection reason remain visible to future proposers.

If cleanup itself fails, the candidate remains rejected and the cleanup failure is recorded as an operational error; it must never be upgraded to accepted.

## 13. Audit model

Every core candidate records a bounded structured audit equivalent to:

```json
{
  "iteration": 3,
  "target": "core",
  "source_id": "llama-cpp-mobile",
  "base_sha": "...",
  "candidate_sha": "... or null",
  "changed_files": ["src/example.cpp"],
  "static_gate": {"status": "pass"},
  "build_gate": {"status": "pass"},
  "regression_gate": {"status": "pass"},
  "performance_gate": {"status": "not_configured"},
  "r_before": 0.61,
  "r_after": 0.68,
  "verdict": "accepted|rejected|invalid",
  "rollback_reason": null
}
```

The Wiki human-readable impact log retains:

- full proposal JSON;
- source and baseline identity;
- actual diff;
- each gate verdict and bounded summary;
- `R_before` and `R_after` when held-out Gate runs;
- final verdict;
- rollback/cleanup outcome.

Rejected experience remains persistent so the proposer can distinguish “never tried” from “built successfully but regressed performance” or other prior failures.

## 14. Runtime state

V0.3 separates operator-authored source manifests from mutable accepted-source state.

Suggested state path:

```text
workspaces/<domain>/sources/state/<source_id>.json
```

State includes at minimum:

```json
{
  "source_id": "llama-cpp-mobile",
  "accepted_sha": "CURRENT_ACCEPTED_SHA",
  "previous_sha": "PREVIOUS_ACCEPTED_SHA",
  "accepted_iteration": 3,
  "updated_at": "ISO-8601 timestamp"
}
```

Resolution rule:

1. first registration verifies manifest `baseline_sha` and creates `refs/wikiskill/<source_id>/accepted` at that SHA when the ref does not yet exist;
2. the namespaced accepted ref is authoritative on every later run;
3. runtime JSON must mirror the ref and is repaired from the ref if they disagree;
4. every later proposal must bind `base_sha` to the current accepted ref SHA;
5. acceptance advances the ref atomically only from the expected old SHA, then updates runtime JSON;
6. rejection never changes the accepted ref or runtime accepted SHA;
7. re-registering an existing `source_id` may update trusted policy only when repository identity and original baseline anchor remain compatible; V0.3 has no implicit baseline-reset operation.

## 15. CLI contract

V0.3 adds operator-facing source inspection/registration commands:

```text
wikiskill source register <manifest>
wikiskill source list
wikiskill source inspect <source_id>
wikiskill source validate <source_id>
```

Semantics:

- `register`: validate and install/update a trusted manifest under explicit operator action.
- `list`: show registered `source_id`, adapter, accepted SHA, and gate configuration summary.
- `inspect`: show one normalized manifest plus mutable accepted-source state; secrets/credentials are never shown.
- `validate`: verify repository resolution, baseline/accepted SHA, allow/deny policy, and registered gate references without applying a candidate.

V0.3 deliberately has no generic `source exec`, arbitrary command, or proposal-triggered registration command.

## 18. Failure handling

Errors are classified into three groups:

### Invalid candidate

Examples: schema error, path violation, stale base SHA, forbidden field.

Behavior: record `invalid`, do not create or continue source execution, no held-out Gate.

### Candidate engineering failure

Examples: static/build/regression/performance fail.

Behavior: record `rejected`, short-circuit later gates, remove candidate worktree, preserve Wiki evidence.

### Operational/infrastructure failure

Examples: repository unavailable, worktree cannot be created/removed, registered gate runner unavailable.

Behavior: candidate is not accepted. Record an operational error separately from a scored capability rejection so future proposers do not incorrectly learn that the patch idea itself was bad.

Operational failure must never advance accepted source SHA or `R_best`.

## 19. Security invariants

V0.3 must preserve all of the following:

- proposals are data, not commands;
- source registration is operator-only;
- repository identity comes from trusted manifest, never proposal;
- gate implementation comes from trusted registry, never proposal;
- proposal cannot widen allowlist or weaken denylist;
- exact baseline/accepted SHA binding is mandatory;
- candidate source mutation occurs only in isolated worktree;
- registered source working tree and Wiki are outside candidate rollback scope;
- no credentials, tokens, signing material, or environment secrets are accepted from or exposed to the proposal path;
- no binary/model-weight mutation in V0.3;
- no automatic cross-repository merge in V0.3.

## 20. V0.4 handoff boundary

After the generic adapter is proven, V0.4 may add source-specific profiles for:

- llama.cpp C/C++/CMake regression and inference benchmarks;
- Android Gradle/NDK builds;
- APK signing/release gates;
- physical-device installation and acceptance;
- S24/S24U performance metrics;
- TTFT / decode tok/s / memory / thermal / power gates;
- ADB/Shizuku device orchestration where explicitly authorized.

Those capabilities must consume the V0.3 Source Registry, Git Source Adapter, and registered-gate interfaces rather than bypassing them.

## 21. Acceptance definition

V0.3 is complete only when a pre-registered Git source can complete this closed loop under automated tests:

```text
WikiSkill proposes a bounded Core Patch
        ↓
source_id + accepted SHA verified
        ↓
isolated worktree created
        ↓
text patch applied within allow/deny policy
        ↓
Static / Build / Regression gates pass
        ↓
Performance pass or explicitly not_configured
        ↓
existing held-out Gate runs
        ↓
strict improvement → accepted source SHA advances
no improvement/failure → complete rollback
        ↓
Wiki retains full audit in both cases
```

The V0.3 release must keep all V0.2 behavior and Python CI green.
