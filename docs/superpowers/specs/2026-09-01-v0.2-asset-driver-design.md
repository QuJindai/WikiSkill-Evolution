# WikiSkill-Evolution V0.2 — Asset-Driver Evolution Architecture

Date: 2026-09-01
Status: Design approved in chat; implementation pending spec review
Base: `main@5e4d81f00b1e8dda212aa4b4590890dd18abdc84`
Upstream basis: `ashutoshsinghpr7/wikiskill@d4072d2e5e2949b0c1346c4158f7e49785d787de`

## 1. Goal

Extend WikiSkill from skill-only evolution into a governed evolution system that can propose and gate four candidate asset classes:

1. `skill` — executable `SKILL.md` packages.
2. `prompt` — workspace-local prompt overlays that change agent behavior without modifying package source.
3. `harness` — declarative execution policy such as turn limits and budgets; no arbitrary Python mutation in V0.2.
4. `core` — a formal manifest/driver contract for external runtime or model-core patches. V0.2 establishes the interface and validation boundaries but does not pretend that an arbitrary JSON edit is a real model-core evolution.

The existing WikiSkill invariants remain unchanged:

- Raw traces are immutable evidence.
- Wiki knowledge persists across rejected candidates.
- Candidate changes are accepted only when held-out validation is strictly better: `R_val > R_best`.
- Rejected candidates are rolled back completely.
- Full rejected proposal content remains visible to future proposers.

## 2. Non-goals

V0.2 will not:

- allow an agent to edit arbitrary repository Python files;
- allow unrestricted shell patches as an evolution candidate;
- modify model weights;
- compile or deploy llama.cpp/Android binaries directly;
- weaken the current validation gate or fresh-sandbox guarantees;
- add third-party Python dependencies.

Core-source mutation and build/test integration are reserved for a later phase after the V0.2 driver contract is proven.

## 3. Architectural decision

Use an **Asset Driver** abstraction rather than branching `gating.py` into target-specific conditionals.

Each driver owns the lifecycle of exactly one candidate asset class:

`prepare/snapshot -> validate proposal -> apply -> diff -> accept or rollback`

The harness owns orchestration and scoring. Drivers never decide whether a candidate is good; the existing gate does.

This preserves one validation algorithm for all asset types and isolates mutation rules by target.

## 4. Proposal contract

### 4.1 Backward compatibility

Legacy proposals remain valid:

```json
{"action":"create","name":"example_skill","skill_md":"..."}
```

If `target` is absent, the harness interprets the proposal as `target="skill"`.

### 4.2 V0.2 envelope

All new proposals use:

```json
{
  "target": "skill|prompt|harness|core",
  "action": "create|patch|no_action",
  "name": "candidate identifier",
  "...": "target-specific payload"
}
```

`no_action` may omit `name` and target-specific payload.

Unknown targets, actions, edit operations, paths, or policy keys fail closed before the validation gate runs.

## 5. Driver interface

Add `wikiskill/assets.py` with a small stdlib-only driver registry and protocol. Concrete drivers expose behavior equivalent to:

```python
class AssetDriver:
    target: str
    def prepare(self, ws: str, iteration: int) -> None: ...
    def validate(self, ws: str, proposal: dict) -> None: ...
    def apply(self, ws: str, proposal: dict) -> str: ...
    def diff(self, ws: str) -> str: ...
    def accept(self, ws: str, iteration: int, score: float) -> None: ...
    def rollback(self, ws: str) -> None: ...
```

The concrete implementation may use functions instead of a formal ABC to keep the package dependency-free and simple. The contract, not inheritance, is mandatory.

Driver lookup is deterministic and explicit. No dynamic import from proposal content is allowed.

## 6. Asset layouts

### 6.1 Skill

Existing layout remains canonical:

`workspaces/<domain>/skills/active/`

The Skill Driver wraps the current Git lifecycle from `gating.py` and preserves the existing behavior and tests.

### 6.2 Prompt overlay

New workspace path:

`workspaces/<domain>/assets/prompts/active/`

V0.2 supports named prompt overlays, beginning with `inference`.

The active inference overlay is appended to the stable package-level `INFERENCE_PREFIX` through `prompts.inference_prompt()`. Package source is not edited during evolution.

Prompt candidates use the same patch operations currently supported for skills: `append`, `replace`, `insert_after`.

The driver permits only files under the prompt asset root and rejects path traversal, absolute paths, and symlink escape.

### 6.3 Harness policy

New workspace path:

`workspaces/<domain>/assets/harness/active/policy.json`

V0.2 policy keys are deliberately small and typed:

- `inference_max_turns`: integer, 1..500
- `maintainer_max_turns`: integer, 1..500
- `proposer_max_turns`: integer, 1..500
- `maintainer_run_budget`: integer, 1..100000
- `proposer_run_budget`: integer, 1..100000

Unknown keys are rejected. The policy modifies orchestration arguments only; it cannot name commands, scripts, paths, environment variables, providers, or credentials.

Defaults preserve the current behavior when no policy exists.

### 6.4 Core manifest

New workspace path:

`workspaces/<domain>/assets/core/active/manifest.json`

V0.2 establishes a safe manifest for future external core integration:

```json
{
  "adapter": "none",
  "source_root": null,
  "build_gate": null,
  "test_gate": null
}
```

In V0.2, `adapter="none"` is the only executable adapter. Core proposals can be parsed, audited, diffed, and rejected as unsupported before validation; they cannot silently mutate repository or device source.

This creates the contract needed for a later `llama_cpp`, Android, or other runtime adapter without opening arbitrary code-write capability in the first release.

## 7. Candidate lifecycle

For every non-`no_action` candidate:

1. Proposer writes one proposal JSON under `runs/proposals/`.
2. Harness normalizes legacy proposals to `target="skill"`.
3. Registry resolves the target driver.
4. Driver validates schema and mutation boundaries.
5. Driver snapshots/prepares the active asset state.
6. Driver applies the candidate.
7. Harness captures a unified human-readable diff.
8. The same held-out validation tasks run through `gating.run_gate()`.
9. If `R_val > R_best`, driver accepts/commits and `R_best` advances.
10. Otherwise driver rolls back only the candidate asset; Wiki persists.
11. State history and Wiki impact log record target, action, candidate description, diff, score, verdict, and previous best.

A driver validation error is not treated as a scored candidate. It is recorded as an invalid proposal and no validation rollout runs.

## 8. Prompt and policy resolution during inference

`prompts.inference_prompt()` becomes workspace-aware while retaining compatibility with existing callers.

The preferred signature is:

```python
inference_prompt(task, sandbox=None, ws=None)
```

If `ws` is omitted or no overlay exists, output is byte-for-byte equivalent to V0.1 behavior.

`gating.run_task()` passes the workspace to prompt construction and resolves the active harness policy before invoking the backend runner.

Maintainer and proposer budgets are resolved in `harness.maintain_step()` and `harness.propose_step()` from the same harness policy with current constants as defaults.

## 9. Audit model

Keep `wiki/skill-impact.md` for backward compatibility in V0.2, but entries become target-aware. A future rename to `evolution-impact.md` is deferred to avoid unnecessary migration churn.

Every candidate outcome records:

- iteration;
- target;
- action;
- name/identifier;
- complete proposal JSON;
- diff when applicable;
- `R_val`;
- previous `R_best`;
- accepted/rejected/invalid/no_action status;
- rollback or commit result.

Rejected and invalid proposals remain permanently visible to the proposer.

## 10. Safety boundaries

All drivers fail closed.

Required checks:

- reject `..` traversal and absolute paths;
- operate only inside the driver-owned workspace asset root;
- reject symlink-based escape where path resolution is relevant;
- reject unknown target/action/edit operation;
- reject unknown harness policy key or wrong value type/range;
- never accept executable command strings from a harness proposal;
- never modify `wiki/` on rollback;
- never run validation after a proposal fails structural validation.

## 11. Compatibility requirements

The following V0.1 behavior is a release gate:

- legacy skill create/patch/no_action proposals still work;
- current Skill Driver accept and reject semantics remain identical;
- fresh sandbox per rollout remains intact;
- zero-tool-call detection remains intact;
- legacy workspaces without `assets/` continue to run;
- existing CLI commands require no mandatory new flags;
- stdlib-only runtime remains intact.

## 12. Test-first implementation gates

Before implementation code, add failing tests for:

1. Legacy skill proposal defaults to `target=skill`.
2. Skill create accept path remains compatible.
3. Skill reject fully rolls back.
4. Prompt candidate changes the generated inference prompt.
5. Prompt ACCEPT persists the overlay.
6. Prompt REJECT restores exact previous prompt state.
7. Harness policy candidate affects runner turns/budget.
8. Harness ACCEPT persists policy.
9. Harness REJECT restores exact prior policy.
10. Unknown harness keys and out-of-range values are rejected before gate.
11. Unknown target is rejected before gate.
12. Path traversal/absolute-path prompt mutations are rejected.
13. Core target is recognized but unsupported mutation fails closed in V0.2.
14. `no_action` performs no validation rollout.
15. Invalid/rejected proposal full content remains in the Wiki audit trail.
16. Existing full test suite remains green.

CI release gate remains:

- `python3 -m pyflakes wikiskill/ tests/`
- `python3 -m pytest tests/ -q`
- Python 3.10 / 3.11 / 3.12 matrix all green.

GitHub Pages failure is explicitly out of scope for this feature and must not be confused with Python CI status.

## 14. Acceptance definition

V0.2 Phase 1 is complete only when:

- the four targets have explicit driver contracts;
- skill, prompt, and harness candidates participate in one common Gate lifecycle;
- core is represented by a safe non-executing contract rather than arbitrary source mutation;
- reject restores the exact pre-candidate state for mutable asset types;
- Wiki evidence survives every reject;
- old workspaces/proposals remain compatible;
- all Python CI matrix jobs pass.
